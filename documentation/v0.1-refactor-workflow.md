# Drafting Table iPad v0.1 refactor workflow

This is the repeatable workflow for continuing the Drafting Table iPad fork
(`Code-Andy/drafting_table`). It describes how to make a reviewable foundation
change, not a generic iOS process. The target is a personal-sideload preview:
one arm64 IPA that can be installed through SideStore or AltStore. App Store
and TestFlight distribution are out of scope unless the owner explicitly asks
for them.

## 1. Safe checkout and baseline

1. Confirm the checkout, remotes, current branch, and worktree status before
   changing anything. A dirty checkout is evidence of someone else's work;
   never overwrite, reset, clean, or switch away from it. Stop and coordinate
   if the requested branch is not clean.
2. Fetch the named fork and create a descriptive branch from the intended fork
   commit (for example, `ipad-v0.1-foundation-refactor`). Do not silently
   replace an existing branch or force-push it.
3. Record the source commits for both the original repository and the fork.
   The original is the design/behavior reference; the fork is the build
   target.
4. Run the portable baseline on Windows. Prefer the checked-in scripts and
   Ninja/Gradle configuration; if `cmake` is not on `PATH`, use the CMake and
   compiler bundled with the installed Visual Studio via its developer
   environment. Capture command, compiler version, test count, warnings, and
   failures in the checkpoint.
5. Inspect the Android renderer and tests before porting a behavior. Classify
   each observed behavior as **normative product intent**, **platform-specific
   reference**, or **known bug/compatibility debt**. Android behavior is not an
   oracle: for example, its bucket fill currently uses the active raster layer
   as the boundary and excludes sibling layers, vectors, and the grid. A
   visible-composite bucket is a product decision, not an automatic parity fix.

## 2. Ownership and transaction contract

Make this contract explicit before adding features. The contract is more
important than the names of individual classes:

```text
UIKit/Pencil input
    -> POD command queue (UI owns no document pixels)
    -> serial document coordinator (metadata, operation IDs, generations)
    -> serial Metal command queue (GPU tile resources and render commits)
    -> immutable checkpoint queue (read-only payloads for undo and I/O)
    -> manifest publication / provider coordination
```

- The document coordinator is the sole serializer of document mutations and
  assigns an `operationID` and monotonically increasing generation.
- Metal is the only writable owner of resident raster pixels. CPU code may
  inspect immutable payloads, but must not mutate a tile concurrently with
  Metal.
- I/O consumes immutable generations and never writes a live GPU tile.
- A raster `TileRecord` contains at least its address, `contentGeneration`,
  `persistedGeneration`, GPU residency/handle, immutable payload reference(s),
  and any in-flight checkpoint token. It has one writable source at a time.
- A tile can be evicted only when no GPU work or readback is in flight and its
  latest content generation is represented by a durable or recoverable payload.
- A Metal commit records affected tile addresses and an atomic before/after
  version (or a deterministic inverse) tied to the completed command-buffer
  generation. The immutable after payload is the source for persistence; the
  before payload is the source for undo. Never publish either version before
  GPU completion.
- Do not perform synchronous full-tile CPU readback on the Pencil/stroke path.
  Use ordered GPU blits, fences, and staging resources; compress/persist after
  completion. This preserves input latency while retaining exact recovery and
  undo semantics.

Snapshots are lightweight metadata plus versioned tile references. Do not copy
an entire page or layer merely to call it immutable.

## 3. Rendering and persistence invariants

- Raster tiles use premultiplied-alpha clear, source-over brush, and
  destination-out true eraser semantics. The eraser reveals lower layers or
  the page background; it does not paint white.
- Layer opacity is applied exactly once to a layer group. Composite raster
  tiles directly when possible. For vector content or a group that needs an
  intermediate, use cached vector tiles or a reusable viewport/scissor-sized
  target; never allocate a full-page offscreen texture per layer.
- Tile addressing is deterministic for negative coordinates and tile seams.
  The same address and generation must identify the same logical content in
  renderer, undo, and archive code.
- Retained DTAR data is a one-way importer at a defined boundary. After the
  tile slice is accepted, do not dual-write DTAR and do not keep it as a live
  rendering fallback.
- For a file package, write immutable, versioned tile payloads (or an
  append-only/SQLite-backed equivalent) first. Build a candidate manifest that
  references complete generations and atomically publish the manifest last.
  Keep the previous manifest until the new one is verified. On recovery, load
  the last complete manifest and garbage-collect unreferenced work only after
  a grace period.
- The logical manifest protocol does not require one physical file per tile.
  Measure loose files versus a packfile or SQLite/WAL container against Files,
  iCloud, interruption, and provider file-count behavior before freezing the
  on-disk layout.

## 4. Review and test gates

Every major step ends with a review before the next step starts. The worker
reports files changed, tests run, known gaps, and assumptions; the integrator
inspects the diff, runs the relevant checks, and records a checkpoint commit.
Agents do not declare completion based only on their own report.

Use two complementary test levels:

1. **Command/document invariants and exact tile tests.** Cover generation
   monotonicity, single-writer transitions, premultiplied alpha, exact
   eraser alpha, grouped opacity (no double application), negative tile
   addresses, atomic before/after undo, manifest recovery, and interruption
   at every commit stage.
2. **Visual goldens with tolerances.** Compare representative brush, eraser,
   opacity, vector, and transform scenes with a documented pixel tolerance.
   Do not blindly golden-test every Android result: exclude behavior classified
   as platform-specific or a known bug, and add a product test for any chosen
   semantic such as bucket boundaries.

Also run device/performance checks for Pencil latency, prediction replacement,
tile upload/readback bandwidth, memory pressure, page reopen time, and a
30-minute drawing session. Windows cannot compile Swift/Objective-C++/Metal;
push checkpoints to the fork and use macOS GitHub Actions/Xcode CI for those
checks.

A simulator launch-only smoke test is insufficient for the raster slice. The
CI smoke must submit at least one synthetic real-sample stroke through the same
public bridge used by Pencil input, wait for manifest publication, then inspect
the persisted `.dtile` and fail if every alpha byte is zero. Physical-device
feedback still overrides simulator confidence for force, latency, hover, and
layout.

## 5. Staged v0.1 gates

Do not estimate or authorize the full feature roadmap until the foundation
gate passes. Use Luna agents at `max` reasoning for bounded implementation and
review work. Reserve a Sol agent for genuinely complex renderer/bridge or
transaction-contract questions. Every delegated task names exclusive files,
non-goals, tests, and the fact that other agents are editing the repository.

### Gate A — repository and contract (about 3–5 working days)

- Complete the safe baseline and Android behavior classification.
- Write the tile authority/state machine, serial ownership rules, operation
  IDs, and transaction/recovery invariants.
- Spike one Metal tile commit with an asynchronous immutable before/after
  checkpoint and one undo/redo round trip.
- Spike the package storage alternatives and provider failure cases.

Pass criteria: no concurrent writable owners, no generation published before
GPU completion, exact tile-level undo, and a recorded storage choice. Re-review
and re-estimate before proceeding.

### Gate B — first useful vertical slice (about 4–8 working weeks)

The first deliverable is intentionally narrow:

- one package-backed document and one page;
- two raster layers;
- Pencil brush and true eraser;
- grouped layer opacity;
- undo/redo from renderer transactions;
- close/reopen and manifest recovery;
- exact pixel/alpha tests plus a small set of tolerant visual goldens;
- a real-device latency and memory smoke test.

No vector editor, selections, snapping, multi-page notebook, or broad UI parity
is required to pass this gate. DTAR can be imported for migration tests but is
not a second live storage or renderer path.

Pass criteria: draw, erase, change opacity, undo, force interruption, reopen,
and observe the same pixels. The gate produces a reviewable v0.1 IPA target
and a revised estimate for everything else.

### Gate C — scale and Apple-provider validation (time-boxed after Gate B)

Add lazy page/tile loading, thumbnails, multi-page metadata, Files/iCloud
coordination, memory-pressure eviction, and interrupted-save recovery. Validate
on physical iPad hardware and with the actual provider used for sideloading.
Re-estimate only after this gate; provider behavior and tile scale are risk
areas, not promises hidden inside a calendar estimate.

Later work (vector editing, selections/transforms, snapping, full UI polish,
accessibility, and parity cleanup) is scheduled only from the Gate C estimate.

## 6. Checkpoint, CI, and IPA handoff

After each gate or major architectural change:

1. Review the diff and portable tests locally.
2. Stage only owned files. If the shared index is dirty, use
   `git commit --only <owned paths> -m "..."`; never reset or include another
   agent's edits. Record the resulting commit hash.
3. Push the checkpoint branch without force. Inspect macOS GitHub Actions for
   Xcode/Swift/Objective-C++/Metal compile and test results and fix Apple-only
   failures before claiming the gate.
4. Build one arm64 IPA from the reviewed commit. Retrieve the exact artifact,
   verify its bundle identifier, version/build, architecture, resources, and
   SHA-256, and store the checksum beside the release notes. The expected
   handoff is one unsigned IPA suitable for SideStore/AltStore re-signing;
   signing certificates and App Store/TestFlight metadata are not assumed.
5. Record device observations and any follow-up as a new bounded task.

## 7. Assumptions record

Every checkpoint ends with a short `Assumptions` section. At minimum record:

- distribution is personal sideloading (one arm64 IPA), not App Store or
  TestFlight;
- iPadOS/device model and Pencil generation used for acceptance;
- chosen bucket-fill boundary semantics and why;
- chosen physical package container and provider test evidence;
- whether a command has deterministic inverse data or before/after tile refs;
- which Android behavior was intentionally not copied;
- unavailable local tools (for example Xcode on Windows) and the CI evidence
  used instead;
- known gaps that prevent calling the build production-ready.

This file is a workflow contract. Update it when a gate exposes a new
invariant, changes the v0.1 scope, or invalidates an assumption.
